# Toolkit pass

In one pass, inspect comments and documentation for factual mismatch; test behavior and missing cases; error handling and swallowed failures; type and API design; correctness, maintainability, and security. For a new error path that discards a resource and schedules a retry, trace the stored state used by the next attempt: whether failure clears or changes it, whether repeated retries can succeed without external change, and what happens as existing resources expire. Scheduling another retry is not itself recovery, but retaining requested state can be intentional. Report the mechanism only when its consequence violates an applicable contract; do not invent a requirement to roll back a failed request or admit a resource with the wrong configuration. For a changed error log level, compare base and head and check whether repeated failures remain visible to operators or callers at default verbosity; report the visibility consequence separately from a commit-message mismatch. Compare a new error variant's display text and doc comment with every path that can produce it, not just the first call site. For changed tests, check that assertions enforce the claimed behavior, including whether they already hold before the changed action, every wait has a failure deadline, and cleanup still runs after an assertion or unexpected exception. A wait without a deadline and cleanup skipped by an exception are distinct hazards even when both can hang the test; cite both mechanisms. Map each changed production branch and client/server path to an actual test stimulus; do not count a test merely because it calls the surrounding method. When a test creates fixtures for both sides, check whether each captured hook is actually invoked and asserted. For a newly added override, compare the base declaration and nearby implementations under supported compile-time guards; a method that overrides only in the default configuration can leave another configuration abstract or fail to compile. For a new wait on queued work, trace every operation needed to settle that work, including peer I/O and shutdown or abort actions sequenced after the wait. Compare base and head ordering before concluding an older flush had the same liveness behavior. For changed docs and test comments, compare the stated consequence or platform coverage with the actual error, assertion, abort, or supported build path. A process-terminating assertion is materially more severe than an ordinary recoverable error; flag documentation that hides that consequence. For a comment claiming no other path waits on a future or state member, inspect later reads of that member. Inspect comments claiming coverage on a particular architecture against source constraints and build configuration; if read-only evidence is insufficient, mark the claim unproven. Check newly added comments against adjacent existing comments for duplication or contradiction. Combine overlapping checks into one finding. Report only a demonstrated defect or rule violation.
