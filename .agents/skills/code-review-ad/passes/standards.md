# Standards pass

Review against applicable, documented repository rules and established conventions supported by specific files. Compare every new test's setup and teardown with nearby tests and contributing guidance, including tracing or logging initialization. Compare a new error variant's display style with adjacent variants and every existing variant that wraps the same inner error; report a pattern mismatch only when it violates an applicable rule or causes a concrete issue. Inspect the PR body and each commit for concrete rule violations, unsupported attribution or validation claims, broken local issue references, a fix split from its test into a later commit, and later fixup commits. For each commit, compare its subject and body with all behavior, public types, and ordering it changes; a subject about one fix may conceal a moved check or another bundled change. If user-level guidance forbids attribution in work authored on the user's behalf, check the PR body and commits for that attribution and cite the guidance; existing older commits do not waive the user's explicit rule. Also inspect changed code for concrete maintenance risks: duplicated nearby explanations, identical adjacent `if` conditions, or scaffolding; loops that repeatedly call the same metric update when one counted operation would suffice; bounded polling sleeps that could use an existing or new notification, or drive the handler directly in a test; new test helpers that repeat existing builders; classifiers that must stay synchronized; unclear test-helper names; fragile references into containers that later edits could invalidate; and new state checks callers could forget. A timeout bounds a poll but does not make its observation deterministic, and lack of an existing signal does not itself make polling the best test structure. For each new lifecycle flag, enumerate every writer of the guarded state, including setup-only paths, and check whether each is guarded or relies only on a comment about call order; report only a current failure or rule violation. Check whether send-like paths or existing predicates omit the flag. Compare newly added or rewrapped documentation lines with the surrounding file's line-length convention, reporting a concrete violation of an applicable documented rule. When a new documentation block sits above an older comment on the same declaration, check for duplicated descriptions and whether the old comment separates the doc block from the declaration. For each new test wrapper, name the behavior it adds and check whether its class name communicates that behavior; report unclear names separately from duplicated forwarding methods. Report rule violations as findings. Omit currently safe maintenance concerns and matters of taste.
